## 5. The actual problem that needs solving

The largest current issue is the model's behaviour on legitimate UDP traffic.

The Mininet testbed successfully demonstrates:

- Six-switch SDN topology.
- Ryu controller registration.
- OpenFlow statistics collection.
- ML API communication.
- End-to-end host connectivity.
- TCP traffic generation.
- UDP traffic generation.
- Capturing benign and attack traffic.
- Flow-level prediction.

However, the existing model has a serious false-positive problem.

### Current Mininet evaluation

The previous audit used the latest snapshot per unique flow tuple rather than counting repeated polling snapshots as separate independent records.

| Traffic category | Correct predictions | Total |
|---|---:|---:|
| Benign ICMP | 6 | 6 |
| Benign TCP | 8 | 8 |
| Benign UDP | 0 | 18 |
| Attack UDP | 18 | 18 |

Overall:

- Benign flows: 14/32 correctly classified.
- Benign false positives: 18.
- Attack flows: 18/18 correctly classified in this small experiment.
- All observed benign UDP flows were incorrectly classified as attacks.
- The sample is too small to claim reliable attack detection.

### Why this is happening

The model makes independent predictions using seven flow-level features.

The original CIC-DDoS2019 training subset does not sufficiently represent the UDP packet-size and traffic patterns observed in our Mininet benign traffic.

A previous data diagnostic found that one sampled collection of CIC benign UDP records had an average-packet-size maximum of approximately 300 bytes, whereas the Mininet benign UDP traffic included packet sizes around 554, 1242 and 1512 bytes.

Our simulated UDP attacks also contained similar packet-size ranges.

Therefore, packet size alone cannot distinguish all benign and malicious UDP flows.

Do not simply raise the probability threshold or retrain the same model and claim the issue is fixed.

### Existing traffic aggregation observation

A previous diagnostic grouped records into approximate polling batches and deduplicated repeated flow snapshots within each batch.

The observed maximum values were:

| Metric | Benign UDP | Attack UDP |
|---|---:|---:|
| Maximum simultaneous source IPs | 3 | 6 |
| Maximum concurrent flows | 3 | 6 |
| Maximum estimated aggregate rate | 15.53 Mbps | 89.50 Mbps |

The largest attack batches had aggregate rates around 89.50, 73.84, 62.38, 54.37 and 31.30 Mbps.

The largest benign batches included approximately 11.23, 7.34, 7.15, 6.95 and 2.86 Mbps.

This suggests that destination-centric traffic aggregation may provide useful evidence that the flow-level classifier is missing.

However:

- These are limited laboratory captures.
- The benign and attack scenarios are not yet a comprehensive workload.
- The 4-source threshold is only a preliminary observation, not a validated general rule.
- The estimated flow rates were derived from cumulative flow counters and durations, not necessarily true per-poll traffic rates.

The new design must use counter deltas over time for accurate interval-rate estimation.

## 6. Research direction and possible contribution

Investigate the following research direction:

### Proposed direction

**A False-Positive-Aware, Destination-Centric Temporal Detection and Mitigation Framework for DDoS Attacks in Software-Defined Networks.**

The proposed system should combine two complementary detection levels:

**Level 1 — Flow-level machine learning**

Use the existing seven-feature ML model to identify suspicious individual flows.

Investigate whether adding better benign UDP training data improves its performance.

**Level 2 — Destination-centric temporal traffic analysis**

For each destination IP, analyse multiple flows over a rolling time window.

Potential features include:

- Number of distinct source IPs targeting one destination.
- Number of simultaneous active flows.
- Aggregate packet rate.
- Aggregate byte rate.
- Change in packet and byte counters between polling intervals.
- Distribution of traffic across source IPs.
- Flow arrival rate.
- Per-source traffic contribution.
- Protocol distribution.
- Source concentration or entropy, if justified by experiments.
- Rate changes across consecutive time windows.

Use destination-level context to distinguish a legitimate high-volume UDP application from a distributed flooding pattern.

Do not hardcode the preliminary 4-source threshold. Estimate thresholds from training and validation experiments, and verify them on independent Mininet runs.

### Important implementation requirement: counter deltas

OpenFlow counters are cumulative for the lifetime of a flow entry.

Do not treat:

```text
byte_count / duration
```

as an accurate instantaneous or per-poll traffic rate.

Maintain previous counter values and timestamps for each suitable flow identity.

For an interval:

```text
delta_bytes = current_bytes - previous_bytes
delta_packets = current_packets - previous_packets

interval_byte_rate = delta_bytes / elapsed_seconds
interval_packet_rate = delta_packets / elapsed_seconds
```

Handle:

- New flows.
- Expired flows.
- Flow counter resets.
- Switch disconnections.
- Duplicate flow observations.
- Reverse-direction aggregation.
- Polling delays.
- Missing statistics replies.
- Counter wrap/reset conditions where applicable.

The existing controller has used approximately 10-second polling. Make the polling interval configurable and investigate whether a shorter interval improves detection latency without creating excessive controller overhead.

### Level 3 — Detection decision and mitigation policy

Design a transparent decision process.

For example:

1. The ML model produces per-flow predictions and probabilities.
2. The destination-level analyser computes traffic features for the current window.
3. A policy combines these independent sources of evidence.
4. Suspicious destinations are flagged.
5. The system logs an alert and its supporting evidence.
6. Mitigation is enabled only after the detection stage has passed validation.

Use a configurable state machine if it improves reliability:

```text
NORMAL
  |
  v
SUSPECTED
  |
  v
CONFIRMED
  |
  v
MITIGATING
  |
  v
RECOVERING
  |
  v
NORMAL
```

Use consecutive-window confirmation, hysteresis or cooldown periods where experiments demonstrate that they reduce false alarms.

Do not use an arbitrary rule merely because it works on the current 18 attack flows.

## 8. Experimental design: required Mininet simulation

A real experimental network testbed is essential. Simply reporting results on CIC CSV files is insufficient for demonstrating the SDN control and mitigation system.


Create reproducible test scenarios.

### Scenario A — Normal traffic only

Include:

- ICMP ping traffic.
- TCP transfers.
- HTTP-like traffic where feasible.
- Ordinary UDP traffic.
- UDP traffic with different payload sizes.
- Low, medium and high UDP rates.
- Multiple legitimate clients accessing the same server.
- More than one legitimate UDP source communicating concurrently.

Crucially, include benign UDP workloads with aggregate rates that overlap with attack workloads.

Otherwise, the classifier may simply learn that high traffic volume means attack.

### Scenario B — Single-source flooding

Generate controlled UDP traffic from one source to the victim.

Vary:

- Packet size.
- Sending rate.
- Duration.

### Scenario C — Multi-source UDP DDoS

Use at least:

```text

```

to send UDP traffic towards h18.

Vary:

- Number of attacking sources.
- Individual source rate.
- Aggregate attack rate.
- Packet size.
- Attack duration.
- Start-time synchronisation.
- Destination port.

### Scenario D — TCP SYN flooding

Implement this only in the isolated Mininet laboratory.

Compare detection and mitigation with UDP detection.

### Scenario E — ICMP flooding

Generate controlled ICMP flooding and evaluate the model separately.

### Scenario F — Mixed benign and attack traffic

This is extremely important.

Have legitimate TCP, ICMP and UDP traffic continue while the simulated attack takes place.

### Scenario G — Low-rate and changing-source attack

Investigate whether the detection system can detect:

- Low-rate attacks.

## 12. Safe mitigation implementation

The current project has automatic mitigation disabled. Keep it disabled by default.

First implement detection-only mode.

Then implement dry-run mitigation that logs what would be blocked without installing drop rules.

Only after the detection results are satisfactory, implement actual mitigation.

Mitigation requirements:

- Restrict experiments to the isolated Mininet topology.
- Use narrowly scoped OpenFlow rules.
- Prefer blocking confirmed malicious traffic towards the victim rather than blindly blocking an entire source host.
- Use configurable timeouts.
- Maintain an allowlist for legitimate traffic and test hosts.
- Log every rule installation and removal.
- Provide an explicit rollback mechanism.
- Avoid permanently blocking a benign host due to one incorrect prediction.
- Demonstrate that legitimate connectivity recovers after mitigation.
- Make mitigation enablement explicit in configuration.

Provide a configuration resembling:

```yaml
detection:
  enabled: true
  mode: observation

mitigation:
  enabled: false
  dry_run: true

monitoring:
  polling_interval_seconds: 5
```

This is an example, not a requirement to replace the existing configuration framework without inspecting it.

Do not silently enable blocking.
