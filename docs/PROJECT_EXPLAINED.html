~/projects/ddos-cicddos2019-ready · study guide

Machine-learning DDoS detection and mitigation in a software-defined network

Everything in this project, from the dataset to the OpenFlow drop rule, explained from zero. Every number on this page was produced by the code in the repository; nothing is estimated.

00The one-minute pitch

We built a small virtual network (18 computers, 6 switches) whose switches are controlled by a program called the controller. Every 5 seconds the controller asks every switch "how many packets and bytes did each conversation send?". It turns those counters into traffic rates, asks a machine-learning model whether each conversation looks like attack traffic, and then looks at the whole picture per victim: how many machines are sending to it, how fast, with what packet sizes, and whether it answers. A second, small model turns that picture into a score. If the score stays high for 2 of the last 3 checks, the controller declares ATTACK CONFIRMED. When mitigation is switched on, it finds the machines responsible and installs a drop rule on each attacker's own switch. The flood stops, legitimate users keep working, and the rules remove themselves when the attack ends.

The research point: a model that looks at one conversation at a time (the "flow-level" model) wrongly flags normal high-volume UDP traffic as an attack. Looking at the victim's whole picture over time fixes most of those false alarms.

01The problem, and why each technology is here

What is a DDoS attack?

A DDoS (Distributed Denial of Service) attack is many machines sending so much traffic to one target that real users can no longer use it. "Distributed" means many sources at once, which is what makes it hard to block: there is no single bad machine.

Analogy: a shop with one door. One rude customer blocking the door is a DoS; you can ask security to remove them. Two hundred people sent by a competitor crowding the door at once is a DDoS; they look like customers, and they come from everywhere.

The attacks used here are floods: a UDP flood (lots of UDP datagrams), an ICMP flood (lots of "ping"-type packets) and a TCP SYN flood (lots of "open a connection" requests that are never completed).

Packet: one unit of data on a network. UDP: a "fire and forget" protocol, no connection, no acknowledgements (used by video, DNS, games). TCP: a connection protocol with acknowledgements (web, file transfer). ICMP: control messages, e.g. ping.

Why SDN?

In a normal network every switch decides for itself where packets go. In SDN (Software-Defined Networking) the switches are "dumb" and a central program, the controller, tells them what to do. That gives two things we need: one place that can see traffic statistics from every switch, and one place that can act by installing a blocking rule on any switch within milliseconds.

Analogy: traditional network = every traffic light runs on its own timer. SDN = a city control room that sees every junction's camera and can change any light remotely.

Why machine learning, and why it was not enough on its own?

Fixed rules like "more than 1000 packets per second is an attack" break easily: a legitimate video stream or file transfer is fast too. Machine learning learns patterns from labelled examples. Our first model learned from a public dataset of real attacks (CIC-DDoS2019). It scored very well on that dataset, but in our network it flagged about half of all legitimate UDP windows as attacks. The reason, found in docs/dataset_audit.md: the dataset's benign UDP is almost all small packets (DNS-like, ~67 B median), while normal bulk UDP in our lab uses 500–1500 B packets, exactly like flood packets. At the level of a single conversation, a legitimate large-packet UDP stream and one flood stream look the same. So the project adds a second, destination-centric layer that looks at all traffic to a victim together. That is the core contribution.

03Building the flow-level ML model (offline)

This happens once, before any demo. The result is a file, artifacts/production/hist_gradient_boosting.joblib. The demo never retrains it.

Step 1 · Dataset data/raw/CICDDoS2019/01-12/

Why
A model can only learn from labelled examples: traffic records already marked "benign" or "attack".
What
CIC-DDoS2019 from the Canadian Institute for Cybersecurity. Three CSV files are used (DrDoS_NTP, Syn, UDPLag): 3,170,293 flow records, of which only 18,462 (0.58 %) are benign. Each row is one flow (one conversation between two IP:port pairs) summarised by a tool called CICFlowMeter, with ~80 columns.
How
Downloaded with scripts/download_cicddos2019.py (public mirror).
When
Once, before training.
Next
The raw CSVs use different column names and units than our switches report, so they must be converted.

Step 2 · Preprocessing ddos_ml/preprocess.py, ddos_ml/features.py

Why
The model must be trained on exactly the same features the controller can compute live from OpenFlow counters. Anything the switch cannot measure is useless at run time.
What
canonicalize_frame() reduces every row to 7 features: protocol, duration (s), packet count, byte count, packet rate, byte rate, average packet size. It also builds the label (0 = benign, 1 = attack) and a group_id.
How
Finds columns by name aliases; converts CICFlowMeter's duration from microseconds to seconds; computes rates; marks impossible values (negative, infinite) as missing. IP addresses, ports and timestamps are never features. They are only used for the group_id, a hash of the conversation (both directions together), so the same conversation can never end up in both the training and test sets. Reads files in chunks of 100,000 rows to fit in memory.
When
Once: python -m ddos_ml.preprocess --input data/raw/... --output data/processed/cicddos2019_flows.csv.
Next
The clean CSV goes to training.
Why "group" splitting matters (data leakage): if pieces of the same conversation are in both training and test data, the model sees the "answers" during training, and test scores look better than reality.

Step 3 · Training and model choice ddos_ml/training.py

Why
To learn a function: 7 numbers in → probability of attack out. And to pick the best algorithm honestly.
What
  1. Remove contradictions: 1,338,471 rows had identical feature values but opposite labels. No model can separate those, so they are dropped (a warning that 7 features cannot describe everything).
  2. Group split: 80 % / 20 % by conversation group (GroupShuffleSplit), overlap verified = 0.
  3. Balance the training part only: 13,386 benign + 13,386 attack rows. The test part keeps its natural mix (3,347 benign, 362,602 attack) so error rates are realistic.
  4. Pipeline: fill missing values with the training median → standardise (scale each feature) → classifier.
  5. Compare 7 algorithms: Random Forest, Extra Trees, Decision Tree, Logistic Regression, KNN, Naive Bayes, HistGradientBoosting.
How
HistGradientBoosting builds many small decision trees one after another, each correcting the mistakes of the previous ones ("boosting"); "Hist" means it bins numbers into histograms to be fast. 160 trees, at most 15 leaves each.
When
Once: python -m ddos_ml.training --input data/processed/cicddos2019_flows.csv → artifacts/production/ (model + metrics.json + plots).
Next
The saved model is served by the prediction API.

Step 4 · The prediction API ddos_ml/predict_api.py, ddos_ml/runtime.py

Why
The model needs Python 3.12 + scikit-learn; the controller runs on Python 3.9. A tiny local web service lets them talk without sharing an environment.
What
GET /health → {"status":"ok", "selected_model":"Hist Gradient Boosting"}. POST /predict with up to 2000 flows → one {"prediction":0|1, "attack_probability":0.0–1.0} per flow.
How
At start-up load_model() checks the metadata (feature list must match exactly; models trained on synthetic demo data are refused). For each request, live_flow_features() rebuilds the same 7 features from the raw counters the controller sends, and the pipeline predicts.
When
Started in Terminal 1, called by the controller every 5-second cycle.
Next
The controller uses the probabilities as Level-1 evidence.
POST /predict  {"flows":[{"ip_proto":17,"duration_sec":30,"duration_nsec":0,"packet_count":7500,"byte_count":7680000}]}
→ {"predictions":[{"prediction":1,"attack_probability":0.99}]}      # a normal 2 Mbit/s UDP stream!

04The network: Mininet, Open vSwitch, OpenFlow and Ryu

Mininet topology Codes/mininet/topology.py (MyTopo), scripts/demo/mininet_lab.py

Why
We cannot attack real machines. Mininet creates a whole virtual network on one Linux machine, where every "host" is an isolated network namespace (its own network card, IP address and processes) and the switches are real Open vSwitch software switches.
What
6 switches in a line, 3 hosts per switch, 100 Mbit/s links. Host hN = 10.0.0.N. Victim h18 on s6. Attackers h1–h6 on s1/s2; legitimate clients h7–h17. 
 h1 h2 h3   h4 h5 h6   h7 h8 h9   h10 h11 h12   h13 h14 h15   h16 h17 h18
    s1 ──────── s2 ──────── s3 ───────── s4 ───────── s5 ───────── s6
How
The demo launcher uses the original MyTopo class unchanged and adds what real measurement needs: hosts not CPU-throttled (the default 5 % CPU per host strangles traffic), NIC offloads off (so counters count real packets, not merged "super packets"), a packet-in rate limit of 500/s per switch (explained below), and services on the victim (iperf3 servers, a web server on :80, a DNS-like server on :5353, silent UDP sinks).
When
Terminal 3, after the controller is up.
Next
Each switch opens a TCP connection to the controller on port 6653 and asks what to do.

OpenFlow in five ideas

OpenFlow 1.3 is the language between controller and switches. You need five ideas:

  1. Flow table. Each switch has a list of rules. A rule = match (which packets, e.g. "UDP from 10.0.0.7:40001 to 10.0.0.18:5203") + action (e.g. "send out port 3", or nothing = drop) + priority (higher wins) + timeouts + counters (packets and bytes matched so far).
  2. Table-miss and packet-in. If no rule matches, the lowest-priority rule (priority 0) sends the packet to the controller. That message is a packet-in.
  3. Flow-mod and packet-out. The controller replies with a flow-mod (install/delete a rule) and a packet-out (send this one packet out of that port).
  4. Flow statistics. The controller can ask "give me all your rules with their counters" (OFPFlowStatsRequest). This is how we measure traffic without touching packets.
  5. Cookie. A 64-bit tag on each rule. Our drop rules carry 0xdd05… so they can be found, counted and deleted precisely.

Analogy: the switch is a post-office sorter with a rule book. Unknown letter → phone head office (packet-in). Head office answers and adds a page to the rule book (flow-mod). Next time that kind of letter arrives, the sorter handles it alone and ticks a counter.

Ryu controller, forwarding part Codes/controller/switch.py (SimpleSwitch13)

Why
Someone has to make the network actually deliver packets, or there is nothing to measure.
What
A "learning switch". It remembers which port each MAC address was last seen on (mac_to_port). When a packet's destination is known, it installs a rule matching the exact conversation: for TCP/UDP the 5-tuple (source IP, destination IP, protocol, source port, destination port), for ICMP the IPs + ICMP type/code. Priority 1, idle timeout 10 s in the demo, hard timeout 100 s. Unknown destinations and ARP are flooded without installing a rule.
How
Ryu is an event-driven framework: methods decorated with @set_ev_cls(ofp_event.EventOFPPacketIn, ...) are called for each packet-in.
When
On the first packet of every new conversation, at every switch along the path.
Next
Because there is one rule per conversation, the rule counters are exactly the per-flow statistics the ML needs. hybrid_controller.py inherits this class and adds detection.
Reactive controller: rules are created only when traffic appears (on packet-in). Side effect we measured: a flood that changes its source port on every packet creates a new rule and a packet-in for every packet, which overloads the controller. This shapes the SYN-flood result.

05Detection, in three levels (every 5 seconds)

All of this runs inside hybrid_controller.py in a background loop (_monitor → _poll_once → _process), once per polling window of 5 seconds.

Collect: counter deltas ddos_ml/temporal_features.py · FlowCounterTracker

Why
OpenFlow counters are totals since the rule was created. "7500 packets in 30 s" is an average over the past; it hides that the last 5 seconds might be a sudden burst.
What
For every rule on every switch, subtract the previous reading → packets and bytes in this window. Handles new rules, rules that expired and came back ("reset"), switches that did not answer (old values kept, no fake zeros), and the same flow seen on several switches (take the maximum, never the sum, or a 6-hop path would count 6 times).
When
Every 5 s, after the replies from all 6 switches (3 s timeout).
Next
The merged per-flow records feed Level 1 and Level 2.

Level 1 · Flow-level ML hybrid_controller._score_ml · ddos_ml/sdn_runtime.py

Why
Use what the CIC-DDoS2019 model knows about attack-shaped conversations.
What
Every active flow gets an attack probability from the API.
How
aggregate_bidirectional_rows() joins the two directions of a conversation (CICFlowMeter flows are two-way, OpenFlow rules are one-way), sends lifetime counters in batches to POST /predict, and writes the probability back onto each flow. If the API is down, detection continues without this evidence and logs an error.
Next
The probabilities become features of the victim's window (e.g. "share of packets from ML-flagged flows").

Level 2 · Destination-centric window features temporal_features.DestinationWindowAnalyzer

Why
A DDoS is defined by its victim: many sources, one destination. You only see that by grouping all flows by destination.
What
For each destination IP, 19 numbers per window, including: n_sources (distinct senders), n_active_flows, pps and bps (packets/bits per second), avg_pkt_size, top_source_share, source_entropy (how evenly spread the senders are), udp/tcp/icmp_share, response_ratio (bytes the destination sends back ÷ bytes it receives; a flood victim answers little), log_pps_change (sudden jump), packet_in_rate, and the Level-1 summaries ml_max_prob, ml_flow_frac, ml_pps_share. It also computes 10 per-source features for every (source → destination) pair: src_pps, src_share, new flows, packets per flow, the source's ML probability, its response ratio, how long it has been active.
Next
The window features are scored by the window model.

Level 2b · The window model decision_engine.LinearScorer · artifacts/experiments/temporal/window_model.json

Why
Combine the 19 numbers into one score in a way you can explain.
What
A logistic regression: score = sigmoid(intercept + Σ weight × standardised feature). Heavy-tailed counts are log-transformed first. The output is between 0 and 1; the threshold is 0.682.
How it was trained
Not on CIC-DDoS2019, but on our own Mininet calibration runs: 14 seeded runs of 7 scenarios (benign only, single flood, multi-source UDP, SYN, ICMP, mixed, low-rate/bursty), 2,063 labelled windows (experiments/scripts/fit_models.py). The threshold was chosen on held-out calibration runs to keep false positives ≤ 2 %. Final numbers were measured on separate test runs never used for fitting. Pure Python, so it runs inside Ryu without scikit-learn.
Strongest weights
n_sources +2.58, avg_pkt_size +2.05, bps +1.69, response_ratio −1.59, pps +1.45, packet_in_rate +1.36, top_source_share −1.22, ml_pps_share −1.06. That last one is negative: the model learned that "the flow-level ML flags these packets" is, on its own, not trustworthy in this network.
Explainable
Each feature's contribution (weight × value) is logged as evidence, e.g. n_sources +5.30, pps +3.40, so every alert says why it fired.

Level 3 · The state machine decision_engine.DecisionEngine.step

Why
One noisy window must not trigger blocking. And blocking must be undone when the attack ends.
What
Each destination is in one state:
NORMAL→SUSPECTED→CONFIRMED→MITIGATING→RECOVERING→NORMAL
  • One window over the threshold → SUSPECTED.
  • 2 of the last 3 windows over → CONFIRMED (k-of-n confirmation).
  • Confirmed + mitigation enabled + attackers identified → rules installed → MITIGATING.
  • While mitigating, the attack still "counts" if the drop rules are hitting ≥ 50 pps. So the rules are not removed while the attacker keeps sending behind them.
  • 2 quiet windows → RECOVERING, rules removed; 2 more quiet windows → NORMAL. New evidence during recovery jumps straight back to CONFIRMED.
When
Once per window, per destination.

Who gets blocked? Source attribution DecisionEngine.attribute_sources · source_model.json

Why
Blocking the victim, or every sender, would complete the attacker's job for them. Only the sources causing the flood should be blocked.
What
For each source sending to the confirmed victim, the rules in experiments/configs/demo.yaml:
  1. A source sending < 50 packets/s to the victim is never blocked (it cannot be causing a flood).
  2. Blocked if the source model (another logistic regression on the 10 per-source features) scores ≥ 0.911, or
  3. if it sends ≥ 800 packets/s and something independent agrees: the flow-level ML flags its flows (p ≥ 0.5), or it opens ≥ 10 new flows per window. Speed alone never gets anyone blocked, because a legitimate file transfer is fast too.
Real example
Rules 1 and 3 were added during testing because the earlier policy, measured live, blocked a legitimate 10 Mbit/s TCP transfer (h7, blocked by speed alone) and a DNS-like client (h10, 0.1 packets/s but many new flows). Both are now spared; see Section 10.

The rule itself hybrid_controller._install_drop

What
match:   eth_type=IPv4, ipv4_src=10.0.0.1, ipv4_dst=10.0.0.18, ip_proto=17 (UDP)
action:  none  (= drop)          priority: 200  (forwarding rules are 1)
where:   only s1, the attacker's own (ingress) switch
cookie:  0xdd05000000000001      hard_timeout: 120 s     flag: tell me when removed
Why this shape
Narrow: h1 can still reach every other host, and the victim with other protocols. At the ingress switch: dropped packets never use the rest of the network. The controller knows the ingress switch because it remembers the first switch that reported each IP. Self-expiring: a forgotten rule disappears after 120 s.
Removal
Automatic on recovery; by the operator via the REST API (DELETE /ddos/rules or /ddos/rules/<cookie>, wrapped by scripts/demo/mitigation_ctl.sh); by switching back to DETECTION_ONLY; or by creating the file experiments/MITIGATION_DISABLE (emergency kill switch).
Proof
Every install/remove is logged and stored as an event. The demo scripts also read the rules directly from the switches (ovs-ofctl dump-flows) so you can show the switch really holds them, with packet counters growing.

07Trace 1: one normal UDP packet, from h7 to h18

h7 runs a legitimate 2 Mbit/s UDP stream to the victim's iperf3 server (1000-byte packets, about 250 per second). Path: h7 → s3 → s4 → s5 → s6 → h18.

  1. t = 0
    h7 kernel · ARP
    h7 knows the IP 10.0.0.18 but not its MAC address. It broadcasts an ARP request ("who has 10.0.0.18?"). s3 has no rule → packet-in to Ryu. Ryu learns "h7's MAC is on s3 port 1" and floods the request. Every switch does the same; h18 answers; the answer travels back the same way, and every switch learns where h18 is.
  2. +1 ms
    s3 · table-miss
    The first UDP packet reaches s3. No rule matches → packet-in. switch.py knows the output port for h18's MAC, so it sends a flow-mod: "UDP 10.0.0.7:40958 → 10.0.0.18:5203 → output port 4, priority 1, idle 10 s", plus a packet-out for this packet. The controller also records host_location[10.0.0.7] = s3.
  3. +3 ms
    s4, s5, s6
    The same happens at each next switch (one packet-in each). From now on every packet of this stream is forwarded by the switches alone, at full speed, without the controller. Each rule's counters tick up.
  4. ≤ 5 s
    controller · poll
    The polling loop asks all 6 switches for their flow statistics. The flow appears on s3, s4, s5, s6; the tracker computes ~1,250 new packets and ~1.28 MB in this 5 s window, and merges the 4 copies into one (max, not sum).
  5. + ~50 ms
    Level 1 · ML API
    The conversation's lifetime counters are sent to POST /predict. The CIC-DDoS2019 model answers probability ≈ 0.99: it thinks this legitimate stream is an attack, the known large-packet UDP false positive.
  6. same cycle
    Level 2 · destination 10.0.0.18
    Window features for the victim: 2 sources (h7 + h13's ping), ~255 pps, 2 Mbit/s, avg packet ~1024 B, one big ML-flagged flow. Contributions: ml_pps_share −2.9, low n_sources, low rate. Score 0.000, far below 0.682.
  7. same cycle
    Level 3 · decision
    State stays NORMAL TRAFFIC. The log shows: [poll 31] dst=10.0.0.18 NORMAL TRAFFIC score=0.000 (thr 0.682) sources=2 flows=2 pps=255 rate=2.09Mbps avg_pkt=1024B | flow-ML max_p=0.99 flagged=50%. Nothing is blocked. This line is the whole project in one sentence: the flow model says attack; the system correctly says normal.
  8. 10 s idle
    switches
    When the stream stops, the rules expire after 10 s without traffic, and the conversation disappears from the statistics.

08Trace 2: a six-source UDP flood against h18

Real timings from the final verification run experiments/results/demo/20261111-224056_mitigation (MITIGATION_ENABLED). Legitimate h7 (TCP 10 Mbit/s), h8 (UDP 2 Mbit/s), h9 (HTTP), h10 (DNS-like) and h13 (ping) were running the whole time. h1–h6 sent UDP floods with different packet sizes (256–1400 B) to different ports, about 12,900 packets/s in total.

  1. −15 s
    baseline
    Only legitimate traffic. Victim NORMAL TRAFFIC.
  2. 0.0 s
    h1–h6 · hping3
    Six attackers start at once. Each flood's first packets miss at every switch → a burst of packet-ins. OVS lets at most 500 per second per switch through to the controller (the rest of that burst is dropped at the switch), so Ryu installs the six flood rules within a second or two without drowning. From then on the flood is forwarded in the data plane.
  3. 0–7 s
    effect on users
    The flood fills the shared links and the controller's queue: HTTP downloads fail (100 % in this phase), DNS-like queries lose 48 %, ping RTT jumps from 0.3 ms to 49 ms. That is the denial of service, measured.
  4. 7.0 s
    first window with the flood
    Victim: 11 sources, ~9,100 pps, 65 Mbit/s, avg packet 888 B, almost no response traffic, packet-in spike, 78 % of flows ML-flagged. Score ≈ 1.0 > 0.682 → SUSPICIOUS TRAFFIC (1 of 3).
  5. 11.7 s
    second window
    Over threshold again → 2 of 3 → ATTACK CONFIRMED. The log prints a DDoS ALERT block: sources, rate, protocol mix, flow-ML probability, strongest evidence, top senders.
  6. 11.7 s
    attribution, same window
    Each attacker sends 900–2,600 pps, its flows are ML-flagged, and its source score is high → all six attributed. h7 (TCP, fast but never ML-flagged, low source score), h8, h9, h10, h13 are not: below the source-model threshold, and either slow or uncorroborated.
  7. 11.7 s
    mitigation
    Six flow-mods: DROP 10.0.0.1/2/3 → 10.0.0.18 UDP at s1, DROP 10.0.0.4/5/6 → 10.0.0.18 UDP at s2. State MITIGATION ACTIVE. Within one second the switches report thousands of dropped packets on each rule.
  8. 14–40 s
    measured effect
    Attack packets reaching the victim's switch: 9,334 pps → 0 pps (−100 %). h7 TCP: 10.0 Mbit/s before, during and after. h8 UDP: 0 % loss throughout. HTTP: back to 0 % failures. DNS-like: back to 0 % loss. h13 ping: 0 % loss. The attackers are still sending; the drop counters keep rising, so the state stays MITIGATING.
  9. 40.1 s
    attack stops
    The drop counters stop increasing.
  10. ~50 s
    recovery
    Two quiet windows → RECOVERING: all six rules deleted (MITIGATION REMOVED … (recovered)). Two more quiet windows → NORMAL TRAFFIC. Total 23.9 s from the end of the attack to a clean state; every former attacker can reach h18 again (ping checked).

10False positives, limitations, and how they are handled

The main false positive, and the fix

A false positive is legitimate traffic treated as an attack; in a system that blocks, it means cutting off real users. Measured on the held-out test campaign (21 runs, not used for fitting; docs/results_summary.md):

MeasureFlow-level ML aloneOur hybrid system
False-positive rate on benign UDP windows50 %3.6 %
False-positive rate, all windows7.6 %1.2 %
False alerts per benign run30.71.3
Attack recall (windows)0.460.81
ICMP flood recall0.001.00
Mean detection latency7.9 s12.4 s

How: the destination-level window (many sources? answering? sudden jump?), 2-of-3 confirmation, attribution by a separate source model with a minimum rate, and corroboration before blocking by rate. The price is a few seconds of extra latency.

Known limitations, all measured

Flash crowd → false alarm. Nine legitimate clients hitting h18 at once (~37 Mbit/s) were CONFIRMED as an attack. With mitigation on, two legitimate large-packet UDP clients (h14, h15) were blocked. Cause: the window model weighs "number of sources" very heavily (+7.1 of the score here) because calibration data rarely had more than a few senders per victim. Measured boundary with this traffic mix: up to 6 concurrent clients stay normal; 8 or more cross the threshold. Fix requires calibration runs with many legitimate clients (not done; retraining was out of scope).

TCP SYN floods are not detected. With random source ports (the realistic form), each SYN is a new rule and a packet-in in this reactive controller, so the attack hits the control plane: about 20,000 short-lived rules, only ~10 SYN/s reaching the victim, and the destination statistics show nearly nothing. With fixed source ports (~12,600 SYN/s reach the victim) the score spikes once at the start (0.98, SUSPICIOUS) then settles at 0.19–0.27: small 73-byte packets that the victim answers do not match what the model learned. Presented as future work.

ICMP floods are detected, but blocking them is unreliable. In the final verification run (ICMP flood + legitimate clients, MITIGATION_ENABLED) the attack was CONFIRMED in 10.4 s but no rule was installed. The attackers' source-model scores were 0.66–0.81, below the 0.911 threshold, and the flow-level ML gives ICMP flows ~0.002 (it is essentially blind to ICMP), so the "fast and corroborated" rule never triggered. An earlier ICMP run did block all six, so the outcome depends on whether one window crosses the source threshold. This is a direct trade-off of the corroboration rule that protects legitimate fast TCP transfers. Possible fix (not applied): accept a lower source score as corroboration, or add an ICMP-specific signal.

Thin margin for normal traffic. One six-client benign run peaked at 0.591 (threshold 0.682); in the final run, one window reached 0.928 (SUSPICIOUS) while flows from the connectivity test that ran just before were still counted (9 sources). It was never confirmed, which is what 2-of-3 confirmation is for, but heavier normal traffic will alarm (see flash crowd).

Lab, not internet. The window and source models were fitted on our own Mininet traffic. They are tuned to this topology, link speed and these tools. A real network would need recalibration.

Reactive controller. Every new conversation costs a packet-in. Without the switch-side packet-in rate limit (500/s), a flood's first packets queued ~1 minute of work at the controller, starving ARP: hosts, legitimate and attacking, stopped sending for ~12 s (measured before the fix).

Attribution is per source, not per packet. A drop rule blocks all UDP (or ICMP, or TCP) from that attacker to that victim, including any legitimate UDP the same host might also send to the victim.

Re-blocking. If an operator removes rules while the attack continues and mitigation is still enabled, the controller re-blocks within 1–2 windows (measured: 8 s). To stop blocking, change the mode.

Tool rate. hping3 achieves about 2,000 packets/s per host, not the 3,000–4,000 configured. Reports always show measured rates.

13Questions a professor or interviewer may ask

Your model has 99.6 % balanced accuracy. Why do you need anything else?

That figure is on CIC-DDoS2019's own held-out data, which has only 3,347 benign test flows and almost no large-packet benign UDP. In our network the same model flagged about half of legitimate UDP windows as attacks. A single flood flow and a single legitimate bulk UDP flow have the same per-flow statistics, so no per-flow model can separate them. The difference only shows at the victim: number of sources, total rate, response, change over time.

Why HistGradientBoosting?

It had the best balanced accuracy and macro-F1 of the 7 candidates on the leakage-safe split (0.996 / 0.923), the lowest false-positive rate tied with KNN, and it is fast and small to serve. KNN scored similarly but must keep the whole training set and is slower to query.

How did you prevent data leakage?

The train/test split is by conversation group (both directions of a 5-tuple hashed together), so no conversation is in both sets; overlap is checked and was 0. Balancing is done after the split, on the training part only. The test set keeps its natural class mix. Identical feature vectors with contradictory labels were removed. For the temporal models, calibration runs and test runs are separate Mininet runs with different seeds.

Why logistic regression for the window model instead of something stronger?

Three reasons: it runs inside the Python 3.9 Ryu process with no libraries (just weights in a JSON file); every decision is a sum of feature contributions, so each alert can explain itself; and the calibration set is small (2,063 windows), where a simple model generalises more safely.

How fast is detection, and why not faster?

About 8.5–11.7 s from attack start to CONFIRMED in the demo runs (one 5 s window to suspect, a second to confirm). Polling faster gives more controller load and the models were calibrated on 5 s windows. Requiring 2 of 3 windows trades a few seconds for far fewer false alarms (30.7 → 1.3 per benign run).

How do you avoid blocking legitimate users?

Blocking needs a confirmed victim, then a per-source decision: a minimum of 50 pps to the victim, and either a high source-model score or (high rate and independent corroboration by the flow ML or new-flow churn). Rules are narrow (one attacker, one victim, one protocol), placed at the attacker's switch, self-expiring, and removed on recovery. We did not use an allow-list; in the tests legitimate TCP, UDP, HTTP, DNS-like and ping clients were not blocked during UDP and ICMP floods. They were wrongly blocked in a 9-client flash crowd, which is a documented limitation.

Does mitigation work for every attack type?

No. Measured: UDP floods are detected and fully blocked with legitimate traffic preserved. ICMP floods are always detected, but blocking is unreliable: in the final run no attacker was blocked, because their per-source scores stayed below threshold and the flow-level model cannot corroborate ICMP. SYN floods are not detected. The stricter blocking policy that protects legitimate fast TCP transfers is what costs ICMP blocking; that is a deliberate safety-over-coverage trade-off, with a proposed fix.

What happens if the ML API crashes?

The controller logs "ML API unavailable" and keeps running Levels 2 and 3 without the flow-level evidence. Forwarding is never affected, because forwarding rules are installed independently of detection.

What if the controller crashes during an attack?

Installed rules stay in the switches. Forwarding rules expire as usual, and drop rules expire after their 120 s hard timeout, so the network cannot be left blocked forever. New conversations cannot be set up until the controller is back, which is the general weakness of a single reactive controller.

Why not detect the SYN flood?

Measured, not guessed: with random source ports, each SYN creates a new rule and a packet-in, so the attack exhausts the control plane and flow table (about 20,000 short-lived rules) while only ~10 SYN/s reach the victim, so the victim-side statistics barely change. With fixed ports the victim sees ~12,600 SYN/s but the model, trained mostly on volumetric UDP/ICMP patterns, scores it 0.19–0.27 after the first window. Fixing it would need packet-in-rate features per source, SYN-specific features, or wildcard forwarding rules.

Why install the drop rule at the attacker's switch and not at the victim's?

Dropping at the edge where the traffic enters frees every link on the path, so other users sharing those links recover too (in the final run, HTTP and DNS-like clients went from 100 % / 48 % failures back to 0 %). Dropping at s6 would protect h18 but leave the chain congested.

What does "SDN makes this possible" actually mean here?

Two concrete things: the controller can read per-conversation counters from every switch with one standard message (flow statistics), and it can push a precise drop rule into any switch within milliseconds. In a traditional network you would need flow-export tools to see the traffic and per-device configuration to block it.

What would you do next?

Calibrate with many-client legitimate traffic to fix the flash-crowd false alarm; add SYN-specific and packet-in-based features; use OpenFlow meters for rate limiting instead of dropping when confidence is lower; proactive or wildcard forwarding to remove the packet-in weakness; and validate on traffic from outside the lab.
